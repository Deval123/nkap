# Which of this repository's own rules are checked, and which are only written

`CONTRIBUTING.md` and `docs/conventions.md` state what a contributor and a maintainer must,
must never and always do. Some of those rules have something that fails when they are broken.
Some are left to a person on purpose. Some were written as if they were checked, and are not.
This page says which is which, one row per rule, so a reader can tell whether anything would
stop them from breaking it.

It is a **dated snapshot of those two files and nothing else**. A rule added to either file
after the date below has no row here, and this page cannot notice that; nothing pretends
otherwise. The ADRs, `SECURITY.md` and the README's promises are a later pass.

| **Money is an integer count of minor units.** No `double` or `float`; one currency per entry; no conversion outside a position account; XAF and XOF have no minor unit. | `conventions.md` "The four rules"; `CONTRIBUTING.md` "Ground rules" | **Instrumented in part: two of its three clauses, to different depths, and the third not at all.** **No `double` or `float`: instrumented.** `check-no-floating-point-money.sh`, run on the real tree and tested by the `no-floating-point-money` job in `build.yml`, blanks comments and string, text-block and char literals, then refuses the words `double`, `float`, `Double` and `Float`, floating-point literals (`1000.0`, `0.75f`, `1e3`), the floating-point half of `Math`, and a short list of double-only APIs, in every module's `src/main/java`. A gap, and not one a script can close yet.** No position account exists in the code: the phrase appears in two error messages, two javadoc comments and their tests. A search of main sources for `rate`, `convert`, `fx` and `conversion` finds no conversion code either, which is a text search and not a proof. The refusal of a mixed entry stops an implicit conversion; it does not stop code that multiplies an amount by a rate and builds a new `Money`. **Also tested:** `Money` is a record over a `long`, `MoneyTest` covers CFA francs and overflow, `CurrencyTest` checks every `Currency`'s `minorUnits()` against an ISO 4217 table, and `LedgerConstraintsIT` asserts `BIGINT` amount columns. ## Why a check is required, or is not

Until now this page recorded, row by row, whether a check is in the ruleset, and never the rule behind it. The rule is written once, at the head of `.github/workflows/build.yml`, and this is the same sentence with its consequences:

**A required check must be able to answer from the branch alone.** Given the files of the pull request it gives the same verdict every time, so it can turn red only because a line of the pull request made it so.

| Check | Reads | Required? |
| --- | --- | --- |
| `dco`, `suppression-expiry`, `trivy-ignore-expiry`, `no-floating-point-money`, `release-tags`, `release-tag-guard`, `compose-project-names`, `image-scan-verdict`, `helm` | Files or the git history of the branch: a script run against the real file or fixtures, or the chart rendered. | Yes. |
| `build`, `demo`, `integration-guide` | The branch's code, built and run. They need the network for what the POMs and Dockerfiles pin. | Yes. An outage can fail them; that is a failure to answer, not a different verdict about the branch. |
| `vulnerability-check` | The NVD, which changes daily. | No, and it will not become so. A CVE published tonight can turn it red on a branch that did not change, and it would block an unrelated merge. |
| `image-scan` | The images published on GHCR. | No, for the same reason. A base image that aged, or a release not yet cut, turns it red with no branch involved (the published 2.2.0 images were red at its last run, on 2026-11-07, for exactly that). |
| `submit-maven` | Describes the dependency tree and judges nothing. | No; see its row. |

What this replaces: sentences that said `vulnerability-check` was "not a required check yet", with the maintainer to add it "once the first findings are triaged" (in the header of `vulnerability-check.yml` and in `CONTRIBUTING.md`, until this change removed them). **That promise was false, kept as history:** the condition was met (the suppression file carries thirteen entries, and the one run of the scan on `main` so far, a dispatch on 2026-11-07, was green) and nothing was added, because the "yet" was wrong from the first day: it described a stage and the reason is a property.

**What this section does not claim.** It states the criterion, and that the checks that are not required fail it, and that the jobs in the first row of the table are of the kind it describes. It is *not* an audit that each of the twelve required jobs is free of every input outside the branch: `build`, `demo`, `integration-guide` and `helm` were not read for a floating image tag, a tool fetched unpinned, or a service they call, and one that has such an input would be a counterexample to the rule as applied. The sentences on this page and in the workflows that say a job is "in the ruleset's required checks" are assertions today; under this rule they become derivable from what a job reads, and checking that is a separate slice.

## Where each dependency instrument is blind

The three instruments that look at dependencies read three different things, and each sees what another cannot. None of them was wrong; each was read as covering more than it does, and the five Jackson CVEs of #301 were the day it showed. Each row of the table says its own part; this is the three side by side.

| Instrument | What it reads | Blind to |
| --- | --- | --- |
| The dependency graph and Dependabot alerts | The resolved tree of `main`, since automatic dependency submission was enabled on 2026-11-07. Before that, only what a POM declares (historical; see the row on the graph). | A branch before it merges; reachability; the operating system layer; anything not in a Maven tree. Fails nothing. |
| `dependency-check` (`vulnerability-check`) | The jars this repository builds, matched to the NVD by CPE, and so only the CVEs the NVD has analysed. | A CVE the NVD has published without CPE data (the five Jackson CVEs), the operating system layer, and `spring-boot-jarmode-tools`, which it does not read. Not required. |
| Trivy on the published images (`image-scan`) | What is actually shipped: the Alpine layer and the jars in the images on GHCR, matched against GHSA and the distribution's own data. | What has not been released yet (the published 2.2.0 images keep reporting what `main` already fixed, until 2.3.0), a pull request, and anything Trivy's database does not know. Not required, and it reports a finding with no fix without failing. |

Read together, the five Jackson CVEs were invisible to `dependency-check` (no CPE data) and, until that evening, to the alerts (no `server` entry), and were seen by the one instrument that reads what ships. The two Spring findings are seen by all three, and are accepted in two places that expire on the same date. That is a description of what was observed on 2026-11-07, not a proof that no fourth blind spot exists.

## What the gaps are, in the order they would be worth fixing

1. **Conversion outside a position account.** The one clause of rule 4 nothing checks, and no position account exists yet to check it against. Until one does, the rule is a sentence; a conversion would arrive as ordinary arithmetic on `Money`, and review is the only instrument.
2. **Assistant attribution and the English rule in commit messages.** A check beside `check-dco.sh` would catch the cases that reach git history, with the limit that it cannot reach pull requests, issues or comments.
3. **Module boundaries, and test scope for `nkap-conformance` and `nkap-test-support`.** They match today. A boundary nothing checks drifts without anyone choosing it, and the table already understates `server`.
4. **Branch name, `Closes #N`, `@DisplayName`.** Each is mechanical and unchecked, and each is cheap on its own.
5. **The by-hand release steps with a mechanical half:** the version a reader copies, the two independent versions, the API-compatibility rule, and reopening `-SNAPSHOT`. The procedure already gives the commands, and a release is rare, so these cost least when they are missed once.
6. **A new provider module with no conformance subclass or provider page.** Two adapters exist and both comply, so this waits for a third.
7. **ADR amendments.** The shape is mechanical and the content is judgment; the first half is worth checking only if amendments become frequent.
