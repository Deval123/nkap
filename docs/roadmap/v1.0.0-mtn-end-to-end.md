# v1.0.0 — MTN, end to end

**Complete: 57/57.** This file was the definition of done for the first release; `v1.0.0`
has shipped, so it is a historical record now, not a plan — work after 1.0.0 is tracked in
issues, not added here.

This is the definition of done for the first release, written down so that it stops being
an intuition. Nothing on this list is optional; nothing off it belongs in 1.0.0 however
tempting. When every box is ticked, the release is cut and the project is announced.

The bet behind this scope: a gateway that genuinely works with one operator is a far
stronger invitation to contributors than a mechanism with eight easy issues. Adding Orange
Money, Wave or M-Pesa is the contribution this architecture was built to accept, and it is
worth more to whoever makes it than writing a simulator scenario.

**Announcement happens at 1.0.0, not before.** There is one first impression.

- [x] Callback for an unknown reference (#7)

- [x] **Scenarios loaded from declarative files — declined for 1.0.0 (#10).** The motivation

      plain data, `POST /_nkap/scenarios` takes the whole declaration as one JSON document,

## 2. MTN adapter — complete, not partial

- [x] Collections: request to pay, status, callback (#24)
- [x] Token lifecycle: cached, renewed ahead of expiry, never on the first 401
- [x] Disbursements: transfer, status, callback (#62). One MTN adapter, two products; a settled disbursement is the ADR 0007 mirror of a collection
- [x] Account balance (#72). Read live, per product; an amount with more precision than the
      currency allows is refused, never rounded; an unanswered read is `ProviderUnavailableException`, never a zero
- [x] Account holder validation (`isaccountholderactive`) (#72). An unanswered check is `ProviderUnavailableException`, never `HolderStatus.INACTIVE`
- [x] **Multi-country.** MTN operates across roughly twenty countries with distinct
      subscription keys and target environments. One deployment serves several, each its
      own adapter with its own `ProviderId` (`mtn-cm`, `mtn-gh`) — not a second adapter, a
      second installation (#82).
- [x] The complete status and error mapping, documented in
      `docs/providers/mtn.md` — including every code that maps to `UNKNOWN` rather than to
      a failure (#92). Checked, not copied: `MtnStatusMappingDocTest` reads the doc table and
      `MtnStatusMap.TABLE` and asserts they agree in both directions.
- [x] The operator's quirks written down: undocumented codes, fields that are sometimes
      absent, sandbox behaviour that differs from production — `docs/providers/mtn.md`,
      including what is still unknown

## 3. The gateway, and the state it keeps

The gateway itself was missing from this list until it was noticed that `server/src` held
no files at all. A roadmap that does not name the thing being built is a roadmap that can
be entirely ticked while nothing runs.

- [x] An HTTP API that creates a payment, hands it to an adapter and reports its state,
      with caller-facing idempotency and honest status codes — a call that did not answer
      is `202` and `UNKNOWN`, never `500` and never `FAILED` (#30). In-memory stores; the
      ledger is untouched, since nothing reaches `SUCCEEDED` without the callback path.
- [x] Callbacks received and **confirmed by `query()` before anything is believed**: a
      webhook can be duplicated, delayed, replayed or forged, and the ledger cannot be
      un-written (#36). Authenticating the endpoint is its own issue — for MTN it is
      source-IP allow-listing, deployment configuration rather than code; confirm-by-query
      is what holds until then.
- [x] A gateway-level test suite holding the two rules the conformance kit cannot: a
      duplicate callback produces one transition, and a callback arriving before the submit
      response is not lost (see §5) (#36)
- [x] Ledger in PostgreSQL, with the invariants as **database constraints**: an entry
      whose postings do not sum to zero cannot be inserted, and entries cannot be updated
      or deleted. A rule that lives only in Java is one a migration script walks through.
      Proved from a SQL client by `LedgerConstraintsIT` (#40).
- [x] Idempotency store persisted, with the same four outcomes as the in-memory reference;
      `begin` atomic on `INSERT … ON CONFLICT`, proved under concurrency (#40)
- [x] Payment state and its history persisted; the history append-only by the same trigger
      as the ledger; every transition attributable (#40)
- [x] Transactional outbox in the same database (ADR 0003) (#77)
- [x] Schema migrations, versioned. **Reversible means a hand-written, tested inverse
      script** beside each migration in `db/rollback` — Flyway's own undo is a paid
      feature. `MigrationRollbackIT` runs each inverse and checks the schema returns to its
      previous state (#40).
- [x] **Several currencies in one deployment.** MTN spans countries using XAF, XOF, GHS,
      UGX, RWF, ZMW and others; this followed directly from multi-country support (#82).
      Float and suspense accounts are per installation, never shared across two countries
      that settle the same currency ([ADR 0009](../adr/0009-accounts-are-per-installation.md));
      payable stays per currency. No conversion — see the out-of-scope section.
- [x] The `Currency` enum is the gateway's own vocabulary — a currency this gateway can
      count in, with its ISO 4217 minor units cross-checked rather than assumed, not a
      mirror of any one adapter's coverage — and membership only grows (#82): ZMW, GNF and
      LRD added. `KES` was briefly removed on an operator-coverage criterion (MTN does not
      operate in Kenya) since withdrawn as the wrong basis for this enum, and is back. See
      the table in `CurrencyTest` and the enum's own javadoc for the sources.

## 4. Operations — what makes it a system rather than a library

- [x] Reconciler for `UNKNOWN` payments: exponential backoff, a configurable window,
      escalation to a human rather than an automatic verdict
- [x] Statement reconciliation: import an operator statement, compare it to the ledger,
      produce a discrepancy report (#56). The parser reads a CSV layout that is ours, a
      placeholder until a real MTN statement is seen
- [x] **Refunds as reversing entries — never as an edit** (#84). "Reversing" means the
      postings run the other way, in a new entry — never `LedgerEntry.reversalOf`, which
      would erase the evidence the merchant was ever paid. A refund is a `DISBURSE` payment
      naming the collection it refunds (`refund_of`), reusing the state machine, settlement,
      reconciler and outbox unchanged; it can time out and go `UNKNOWN` exactly like any
      other transfer, and nothing writes a ledger entry before the operator confirms it. The
      one new rule: an in-flight refund reserves its amount the moment it is created, not
      only once it settles, so two refunds for half a collection cannot both pass the cap
      while both are still in flight — see ADR 0010.
- [x] Outgoing webhooks: HMAC-SHA256 signature with a timestamp, at-least-once delivery,
      exponential backoff, dead-letter queue, replay from the console or the API (#77).
      Replay is the API shape — `POST /webhooks/events/{eventId}/replay`, admin-gated —
      not a console command; see the pull request for why.
- [x] Prometheus metrics, including **the suspense account balance** — the single most
      useful alert in the system (#75). Computed live on every scrape, never cached; a
      computation failure reports `NaN`, never a healthy-looking zero. Three alerting
      rules — this gauge, an escalated payment and a dead-lettered webhook event — ship
      in `docs/prometheus-alerts.yml`
- [x] Structured logs correlated by reference across every component (#75). The payment
      reference, a reconciler pass id and a statement import id travel as `MDC` fields,
      not only inside the sentence, on `PaymentService`, `SettlementService`, `Reconciler`
      and `StatementReconciliation`
- [x] **Callers are authenticated, and a merchant sees only its own payments.** Added to this
      list after it was written, deliberately, because §6 changes what its absence means: a
      library someone integrates behind their own proxy leaves the choice to them, but a
      published image and a two-command install is an invitation, and somebody will put a
      payments gateway on the internet with no credential in front of it. It also closes a
      real hole — the merchant id arrives in the request body today, so idempotency is scoped
      by a field the caller invents. The callback endpoint stays unauthenticated: the operator
      sends no credential, and it is safe because it only ever triggers a confirming query.

## 5. Conformance kit — the door held open for the second operator

Adapter-level rules, extracted from tests already proven against MTN. The kit lives in
`conformance/`; see its README.

- [x] The same reference submitted twice produces one payment
- [x] A timeout followed by a successful query resolves to `SUCCEEDED`, never `FAILED`
- [x] An outright refusal yields `SubmitResult.Rejected`
- [x] A flapping status never reopens a terminal payment
- [x] An expired token mid-flight is renewed and the call retried with the same reference
- [x] A callback for a reference the gateway never issued is rejected without writing anything
- [x] Runnable against any adapter with no account and no dependency on the simulator
- [x] A code the adapter does not recognise maps to `UNKNOWN`, never `FAILED`

A duplicate callback producing one state transition, and a callback arriving before the
submit response not being lost, are **not** in this kit: they are properties of the
gateway's state machine and idempotency store, not of an adapter. They belong to a
gateway-level suite once `server` exists.

## 6. Adoption — the first thirty minutes of a stranger

One rule shapes this section: **you clone to contribute, you pull an image to use.** A
project that requires a checkout and a build before it can be tried only ever gets users who
are also Java developers, and most of the people this exists for are not.

- [x] `docker compose up` from a clone starts the gateway, PostgreSQL and the simulator, and
      a documented command puts one payment through end to end. This is the contributor's
      path.
- [x] **The gateway published as a Docker image** on a public registry, tagged per release
      and with a moving `latest`. Nothing about running Nkap should require a JDK. (#86,
      `.github/workflows/release.yml`, on an annotated `v*` tag and nowhere else)
- [x] **A standalone compose file**, downloadable on its own and referencing published
      images rather than building from source, so that installing is two commands and no
      checkout. The Helm chart and every install instruction depend on this image existing;
      without it the only path is a clone. (#86, `nkap-standalone.compose.yaml`)
      **It provisions no API key.** `compose.yaml` in this repository creates one, named
      `nkap_demo-key-not-for-production-000000000000000`, because a demo needs a credential and that file is
      only ever a demo. Deriving the standalone file from it — the obvious way to write it —
      would put a default credential, published in a public repository, in front of a real
      payments gateway. The standalone file asks the operator to provision a key and refuses
      to start without one; a service that will not start is a better failure than one that
      starts with a key everyone knows.
- [x] The simulator image usable entirely on its own, documented for developers who will
      never run the gateway — the most numerous audience, and the project's front door. (#86,
      README's "The simulator on its own")
- [x] OpenAPI specification, published (#88). `docs/openapi.yaml`, hand-written and checked
      against the running application by `OpenApiSpecIT` on every build — a file in the
      repository, not served, not generated: see that file's own header for the argument.
- [x] Integration guide with runnable `curl` examples (#88). `docs/integration-guide.md`;
      every command in it is extracted and executed for real by
      `examples/run-integration-guide.sh`, in its own CI job.
- [x] Configuration reference: every setting, its default, and what happens when it is wrong
      (#90, `docs/configuration-reference.md`). Kept honest against
      `ReconcilerProperties`/`OutboxRelayProperties`/`MtnProperties` by
      `ConfigurationReferenceTest` — see that file's own "How this table is kept honest"
      section for exactly what the drift check covers and what it deliberately does not.
- [x] Kubernetes deployment (Helm chart or Kustomize base) (#101, `charts/nkap`). No
      credential value is ever accepted in `values.yaml` — every one is the name of a
      `Secret` the operator created, and rendering fails naming what is missing, the same
      rule `nkap-standalone.compose.yaml` set with `${VAR:?message}`. The chart's own
      README answers three questions a compose file never forced: where the first API key
      appears and who else can read it (a new exposure, since `kubectl logs` is not
      `docker compose logs`), what runs the migrations with more than one replica (nothing
      separate — Flyway's own lock, and the rolling-upgrade constraint that follows from
      that, written down rather than assumed away), and whether more than one replica is
      safe at all (yes, and the mechanism is named: `SELECT ... FOR UPDATE SKIP LOCKED` in
      the reconciler and the outbox relay, the payment row lock in settlement). CI renders
      the chart and asserts the traffic `Service` never carries the management port and
      that a values file with no credentials fails to render — it does not install into a
      real cluster; the chart's own README names that as what remains unproven.
- [x] Security notes: credential handling, webhook verification, what Nkap does and does
      not protect (#90, `docs/security-notes.md`). Three things 1.0.0 deliberately does
      **not** do belong here by name, each with the reason it was left out rather than a
      silence a reader has to interpret — drafted here, refined in the shipped file (the
      key-rotation bullet below overstates what exists; `docs/security-notes.md` says
      precisely what does: a direct database delete, not an application command):
      - **Rate limiting.** A reverse proxy does this better and it is its job. Caller
        authentication was in scope precisely because no proxy can know your merchants;
        this is the opposite case. What a proxy cannot do is cap calls per authenticated
        merchant to protect the operator's quota — worth revisiting when a deployment has
        enough merchants for that to bite.
      - **Key rotation and revocation.** The primitives already exist: revoking is deleting
        the row, rotating is creating the new key, switching, then deleting the old one.
        What is missing is the sentence saying so, not the code.
      - **An audit trail of which key did what.** The payment history already answers what
        happened and why. Who asked starts to matter when a merchant holds several keys,
        which is not 1.0.0.

## Explicitly out of scope for 1.0.0

Listed so the scope cannot grow quietly. Each of these is a good idea for later.

- **Any operator other than MTN.** Orange Money, Wave, M-Pesa and Airtel come after 1.0.0,
  and they are what contributors are invited to.
- **Foreign exchange.** Several currencies are supported and required (see §3); what is
  excluded is converting between them. Conversion needs a rate, a date, a position account
  and a revaluation policy, none of which belongs in a first release. A consequence worth
  stating: Nkap will not report a total balance across currencies, because that total does
  not exist without a rate, and inventing one is how a ledger starts lying.
- A merchant dashboard or any user interface.
- KYC, AML, sanctions screening.
- Generated client SDKs.
- Holding funds. Money stays at the operator; Nkap records, it does not custody.
- Becoming a licensed payment institution.
