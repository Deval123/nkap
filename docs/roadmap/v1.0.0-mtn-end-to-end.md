# v1.0.0 — MTN, end to end

This is the definition of done for the first release, written down so that it stops being
an intuition. Nothing on this list is optional; nothing off it belongs in 1.0.0 however
tempting. When every box is ticked, the release is cut and the project is announced.

The bet behind this scope: a gateway that genuinely works with one operator is a far
stronger invitation to contributors than a mechanism with eight easy issues. Adding Orange
Money, Wave or M-Pesa is the contribution this architecture was built to accept, and it is
worth more to whoever makes it than writing a simulator scenario.

**Announcement happens at 1.0.0, not before.** There is one first impression.

## 2. MTN adapter — complete, not partial

- [x] Collections: request to pay, status, callback (#24)
- [x] Token lifecycle: cached, renewed ahead of expiry, never on the first 401
- [ ] Disbursements: transfer, status, callback
- [ ] Account balance
- [ ] Account holder validation (`isaccountholderactive`)
- [ ] **Multi-country.** MTN operates across roughly twenty countries with distinct

- [ ] The complete status and error mapping, documented in
      `docs/providers/mtn.md` — including every code that maps to `UNKNOWN` rather than to

- [x] The operator's quirks written down: undocumented codes, fields that are sometimes
      absent, sandbox behaviour that differs from production — `docs/providers/mtn.md`,
      including what is still unknown

## 3. The gateway, and the state it keeps

The gateway itself was missing from this list until it was noticed that `server/src` held
no files at all. A roadmap that does not name the thing being built is a roadmap that can
be entirely ticked while nothing runs.

- [x] An HTTP API that creates a payment, hands it to an adapter and reports its state,
      with caller-facing idempotency and honest status codes — a call that did not answer
      is `202` and `UNKNOWN`, never `500` and never `FAILED` (#30). In-memory stores; the
      ledger is untouched, since nothing reaches `SUCCEEDED` without the callback path.
- [ ] Callbacks received, authenticated, and **confirmed by `query()` before anything is
      believed**: a webhook can be duplicated, delayed, replayed or forged, and the ledger
      cannot be un-written
- [ ] A gateway-level test suite holding the two rules the conformance kit cannot: a
      duplicate callback produces one transition, and a callback arriving before the submit
      response is not lost (see §5)
- [ ] Ledger in PostgreSQL, with the invariants as **database constraints**: an entry
      whose postings do not sum to zero cannot be inserted, and entries cannot be updated
      or deleted. A rule that lives only in Java is one a migration script walks through.
- [ ] Idempotency store persisted, with the same four outcomes as the in-memory reference
- [ ] Payment state and its history persisted; every transition attributable
- [ ] Transactional outbox in the same database (ADR 0003)
- [ ] Schema migrations, versioned and reversible
- [ ] **Several currencies in one deployment.** MTN spans countries using XAF, XOF, GHS,
      UGX, RWF, ZMW and others, so this follows directly from multi-country support.
      Float, payable, fee and suspense accounts are per currency; balances and
      reconciliation are per currency; an entry never mixes two. No conversion — see the
      out-of-scope section.
- [ ] The `Currency` enum covers every country the adapter targets, with the right number
      of minor units for each. Derive the list from MTN's actual coverage rather than from
      memory: at least ZMW, GNF and LRD are missing today, and XAF/XOF have no minor unit
      while GHS and NGN have two.

## 4. Operations — what makes it a system rather than a library

- [ ] Reconciler for `UNKNOWN` payments: exponential backoff, a configurable window,
      escalation to a human rather than an automatic verdict
- [ ] Statement reconciliation: import an operator statement, compare it to the ledger,
      produce a discrepancy report
- [ ] Refunds as reversing entries — never as an edit
- [ ] Outgoing webhooks: HMAC-SHA256 signature with a timestamp, at-least-once delivery,
      exponential backoff, dead-letter queue, replay from the console or the API
- [ ] Prometheus metrics, including **the suspense account balance** — the single most
      useful alert in the system
- [ ] Structured logs correlated by reference across every component

## 5. Conformance kit — the door held open for the second operator

Adapter-level rules, extracted from tests already proven against MTN. The kit lives in
`conformance/`; see its README.

- [x] The same reference submitted twice produces one payment
- [x] A timeout followed by a successful query resolves to `SUCCEEDED`, never `FAILED`
- [x] An outright refusal yields `SubmitResult.Rejected`
- [x] A flapping status never reopens a terminal payment
- [x] An expired token mid-flight is renewed and the call retried with the same reference
- [x] A callback for a reference the gateway never issued is rejected without writing anything
- [x] Runnable against any adapter with no account and no dependency on the simulator
- [ ] A code the adapter does not recognise maps to `UNKNOWN` — proven at unit level;
      joins the kit when issue #26 makes it drivable through a harness

A duplicate callback producing one state transition, and a callback arriving before the
submit response not being lost, are **not** in this kit: they are properties of the
gateway's state machine and idempotency store, not of an adapter. They belong to a
gateway-level suite once `server` exists.

## 6. Adoption — the first thirty minutes of a stranger

One rule shapes this section: **you clone to contribute, you pull an image to use.** A
project that requires a checkout and a build before it can be tried only ever gets users who
are also Java developers, and most of the people this exists for are not.

- [ ] `docker compose up` from a clone starts the gateway, PostgreSQL and the simulator, and
      a documented command puts one payment through end to end. This is the contributor's
      path.
- [ ] **The gateway published as a Docker image** on a public registry, tagged per release
      and with a moving `latest`. Nothing about running Nkap should require a JDK.
- [ ] **A standalone compose file**, downloadable on its own and referencing published
      images rather than building from source, so that installing is two commands and no
      checkout. The Helm chart and every install instruction depend on this image existing;
      without it the only path is a clone.
- [ ] The simulator image usable entirely on its own, documented for developers who will
      never run the gateway — the most numerous audience, and the project's front door.
- [ ] OpenAPI specification, published
- [ ] Integration guide with runnable `curl` examples
- [ ] Configuration reference: every setting, its default, and what happens when it is wrong
- [ ] Kubernetes deployment (Helm chart or Kustomize base)
- [ ] Security notes: credential handling, webhook verification, what Nkap does and does
      not protect

## Explicitly out of scope for 1.0.0

Listed so the scope cannot grow quietly. Each of these is a good idea for later.

- **Any operator other than MTN.** Orange Money, Wave, M-Pesa and Airtel come after 1.0.0,
  and they are what contributors are invited to.
- **Foreign exchange.** Several currencies are supported and required (see §3); what is
  excluded is converting between them. Conversion needs a rate, a date, a position account
  and a revaluation policy, none of which belongs in a first release. A consequence worth
  stating: Nkap will not report a total balance across currencies, because that total does
  not exist without a rate, and inventing one is how a ledger starts lying.
- A merchant dashboard or any user interface.
- KYC, AML, sanctions screening.
- Generated client SDKs.
- Holding funds. Money stays at the operator; Nkap records, it does not custody.
- Becoming a licensed payment institution.
