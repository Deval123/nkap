# Which of this repository's own rules are checked, and which are only written

`CONTRIBUTING.md` and `docs/conventions.md` state what a contributor and a maintainer must,
must never and always do. Some of those rules have something that fails when they are broken.
Some are left to a person on purpose. Some were written as if they were checked, and are not.
This page says which is which, one row per rule, so a reader can tell whether anything would
stop them from breaking it.

It is a **dated snapshot of those two files and nothing else**. A rule added to either file
after the date below has no row here, and this page cannot notice that; nothing pretends
otherwise. The ADRs, `SECURITY.md` and the README's promises are a later pass.

- **Read at:** commit `b1bc147` (2026-11-07). The workflow jobs, scripts, POMs and tests named
  below were opened and read at that commit.
- **Repository settings** (the `main` ruleset, merge methods, branch deletion, private
  vulnerability reporting) are not in any commit. They were read from the GitHub API on the same
  day, and can change without a pull request showing it.
- **"Deliberately not"** means the repository says so itself, or the rule is a judgment that no
  script could make. Where the repository records the choice, the row cites it; otherwise it is
  this page's reading, and a maintainer is free to disagree.
- **Prose that is not a rule** (for example "the hardest contribution to get merged is a change
  to `core`") has no row. Neither does a rule that is now history, such as the scope of v1.0.0.

The instruments are the eight jobs in `.github/workflows/build.yml` (`build`, `demo`,
`integration-guide`, `release-tags`, `release-tag-guard`, `dco`, `compose-project-names`,
`helm`), the four jobs in `.github/workflows/release.yml`, the scripts under `.github/scripts/`,
the settings above, and tests in the reactor. The ruleset requires exactly those eight `build.yml`
jobs before anything merges into `main`.

## The rules

| The rule | Where it is written | What enforces it |
| --- | --- | --- |
| Every commit is signed off (`git commit -s`), and the trailer matches the commit's author by name or by email. | `conventions.md` "Commits"; `CONTRIBUTING.md` "Pull requests", "License" | **Instrumented.** The `dco` job in `build.yml` runs `.github/scripts/check-dco.sh` over the pull request's own commit range, and `check-dco.test.sh` asserts the script. It skips merge commits, fails a commit with no trailer or with one matching neither name nor email, and fails an empty range rather than passing on nothing. The ruleset requires `dco`. It runs on pull requests only. |
| Nothing is committed straight to `main`, not even by the maintainer; a release commit goes through a pull request. | `conventions.md` "Branches and pull requests"; `CONTRIBUTING.md` "Versioning and releases" step 2 | **Instrumented, by a setting.** The `main` ruleset is active, requires a pull request, has no bypass actors, and forbids deletion and non-fast-forward pushes. It lives in repository settings, not in a file. |
| The build is green before merging; `main` is always green. | `conventions.md` "Branches and pull requests" | **Instrumented, with two limits.** The ruleset requires all eight `build.yml` jobs, and `build` runs the full reactor with `-Dnkap.docker.required=true`, so the integration tests cannot be skipped. The ruleset does not require a branch to be up to date with `main` (`strict_required_status_checks_policy` is false), so two pull requests that are green separately can be red together. `build.yml` also runs on every push to `main`, which reports a red `main` after the fact and does not prevent one. |
| Merge with a rebase or a merge commit, not a squash. | `conventions.md` "Branches and pull requests" | **Not instrumented. A gap.** The repository allows squash merging (`allow_squash_merge` is true) and the ruleset's allowed merge methods include `squash`. Removing it from both is a settings change. |
| Delete the branch after merging. | `conventions.md` "Branches and pull requests" | **Instrumented, by a setting.** `delete_branch_on_merge` is true. |
| One issue, one branch, one pull request; the branch is named `<type>/<issue>-<slug>`. | `conventions.md` "Branches and pull requests" | **Not instrumented. A gap.** No job or ruleset looks at a branch name. A branch-name rule in the ruleset, or a job reading `github.head_ref`, could check the pattern. "One issue, one pull request" is a judgment and stays one. |
| The pull request closes its issue with `Closes #N`. | `conventions.md` "Branches and pull requests" | **Not instrumented. A gap.** There is no pull request template and no job reads the description. A job could require a closing keyword unless the branch is the no-issue form. |
| Nothing the repository publishes carries assistant attribution: not a commit, not a pull request, not an issue or a comment. | `conventions.md` "Commits" | **Not instrumented. A gap.** `check-dco.sh` reads the trailers of each commit and looks for nothing else. A check over commit messages could be added beside it. It could never reach a pull request description, an issue or a comment, which are not in git history. |
| Everything committed is in English. | `conventions.md` "Language" | **Not instrumented. A gap, and a hard one.** Nothing detects a language. A check on commit subjects could catch the obvious case, and a reviewer is the instrument for the rest. |
| A commit subject is imperative and under 72 characters; the body says why; one concern per commit and per pull request. | `conventions.md` "Commits"; `CONTRIBUTING.md` "Pull requests" | **Not instrumented, deliberately** (this page's reading), except that the length is mechanical and could be checked. Whether a body says why, and where one concern ends, is review. |
| Comments explain why, never what. | `CONTRIBUTING.md` "Pull requests" | **Not instrumented, deliberately.** A judgment about meaning. |
| New behaviour comes with a test; in `core`, the test comes first. | `conventions.md` "Tests"; `CONTRIBUTING.md` "Pull requests" | **Not instrumented, deliberately** (this page's reading). No coverage tool is configured in any POM, and a test written first leaves no trace in the final diff. |
| Test names are sentences stating the rule, in `@DisplayName`. | `conventions.md` "Tests"; `CONTRIBUTING.md` "Pull requests" | **Not instrumented. A gap.** Nothing fails on a `@Test` without a `@DisplayName`. That half is cheap to check; whether the sentence states a rule is not. |
| **The ledger is append-only.** No `UPDATE` or `DELETE` on entries; a mistake is a reversing entry. | `conventions.md` "The four rules"; `CONTRIBUTING.md` "Ground rules" | **Instrumented.** `V1__initial_schema.sql` puts `BEFORE UPDATE OR DELETE` triggers on `ledger_entry`, `posting` and `payment_transition`, and `LedgerConstraintsIT` ("UPDATE and DELETE on a recorded ledger entry are refused from the application's own connection") runs all four statements against them. It needs Docker, which `build` requires in CI. `InMemoryLedgerTest` only shows that the in-memory ledger's history list is unmodifiable. The idempotency store is not append-only, and its migration comment says so. |
| **A timeout is never a failure.** An unreadable, absent or unrecognised response maps to `UNKNOWN`. | `conventions.md` "The four rules"; `CONTRIBUTING.md` "Ground rules" | **Instrumented, in two layers.** In `core`, `PaymentStateTest` ("a timeout moves a payment to UNKNOWN, never to FAILED"). For every adapter, `ProviderAdapterConformanceTest` ("a call that does not answer yields UNKNOWN, never a failure", "an operator answer the adapter cannot map is UNKNOWN, never FAILED"), run by `MtnConformanceTest` and `MpesaConformanceTest`. The rule says *no code path*; these cover the state machine and each adapter's mapping. I did not trace the gateway's own code paths, so a new one outside both layers is covered only if some test happens to exercise it. |
| **`core` has no dependencies.** No Spring, web, JSON library or ORM; `provider-api` depends only on `core`. | `conventions.md` "The four rules", "Module boundaries"; `CONTRIBUTING.md` "Ground rules" | **Not instrumented. A gap, and one of the four.** Today `core/pom.xml` declares no dependency and `provider-api` declares only `nkap-core`. Spring Boot is imported as a BOM, so it cannot arrive through a parent. But no POM configures an enforcer, ArchUnit or any similar rule, and a dependency added to `core` would build and pass. (JUnit reaches every module at test scope from the root POM, by design.) |
| **Money is an integer count of minor units.** No `double` or `float`; one currency per entry; no conversion outside a position account; XAF and XOF have no minor unit. | `conventions.md` "The four rules"; `CONTRIBUTING.md` "Ground rules" | **Instrumented in part.** `Money` is a record over a `long`, and `MoneyTest` covers CFA francs, mixed currencies and overflow. `CurrencyTest` checks every `Currency` member's `minorUnits()` against an ISO 4217 table and fails on a member missing from it. `LedgerConstraintsIT` asserts `BIGINT` amount columns and that a mixed-currency entry cannot be expressed. **Not covered:** nothing scans for a `double` or `float` in new code, and nothing checks conversion. Two metrics gauges legitimately return `double`, so a scan would need to allow for them. |
| The module boundaries table: what each module depends on, `test-support` and the simulator faces at test scope only, `simulator-core` never a face module. | `conventions.md` "Module boundaries" | **Not instrumented. A gap.** Every module's `<dependency>` list matches the table today, except that `server` also depends on `core`, `provider-mtn` and `provider-mpesa` at compile scope, which its row does not say. Nothing fails if one of them changes. |
| Spring Boot is imported as a BOM in the root POM, never as a parent. | `conventions.md` "Module boundaries" | **Not instrumented. A gap.** The root POM imports `spring-boot-dependencies` with scope `import` and has no `<parent>`. Nothing keeps it so. It matters only because `core` stays free of Spring this way. |
| An adapter translates and never decides; transitions, idempotency and bookkeeping live in `core`. | `conventions.md` "Module boundaries" | **Not instrumented, deliberately** (this page's reading). A design rule; the conformance kit above covers the part of it that is behaviour. |
| Every adapter passes the conformance kit; it is "not optional and not adjustable". | `CONTRIBUTING.md` "Adding an operator" step 2 | **Instrumented for the two adapters that exist; not for a third.** `MtnConformanceTest` and `MpesaConformanceTest` extend the kit, and both run in `build`. Nothing fails if a new `provider-<name>` module has no such class, since modules are listed by hand in the root POM. |
| `nkap-conformance` and `nkap-test-support` are depended on at test scope only. | `CONTRIBUTING.md` "Adding an operator" step 2; `conventions.md` "Module boundaries" | **Not instrumented. A gap.** Every current use is at test scope (read in each POM). Nothing enforces it. |
| Each operator's quirks are documented in `docs/providers/<name>.md`. | `CONTRIBUTING.md` "Adding an operator" step 3 | **Instrumented in part.** `mtn.md` and `m-pesa.md` exist. `MtnStatusMappingDocTest` checks `mtn.md`'s status table against `MtnStatusMap` in both directions. Nothing checks that a provider module has a page, and no test guards `m-pesa.md`'s tables. |
| An ADR is amended in place, with a dated `## Amendment` section and an inline marker on every affected passage; the decision text and its reasoning are never edited; a superseding ADR only when the decision is replaced. | `CONTRIBUTING.md` "Amending an ADR" | **Not instrumented. A gap, partly deliberate.** Nothing checks the heading format, the inline marker, or that the original text is untouched. A check could compare a pull request's diff against the ADRs. Choosing amend over supersede is a judgment. |
| The release commit moves `docs/openapi.yaml`'s `info.version` and the chart's `version` when, and only when, they changed. | `CONTRIBUTING.md` "Versioning and releases" step 1 | **Not instrumented. ## What the gaps are, in the order they would be worth fixing

1. **`core` has no dependencies.** `conventions.md` says the four rules are enforced by tests, and for this one there is no test, and no enforcer rule in any POM. It is the rule the architecture rests on, and nothing fails if it breaks.
2. **Money has no `double` or `float` in new code.** The type and the columns are tested; the rule as written ("no `double`, no `float`") is not, and a scan needs a small allowance for two metrics gauges.
3. **Tags are annotated.** Both documents say tags are annotated (`CONTRIBUTING.md` adds "never lightweight"), and a lightweight tag publishes today. Reading the tag's type in the guard is a few lines.
4. **No squash merge.** The one rule about merging that the repository's own settings contradict, and the cheapest to close.
5. **Assistant attribution and the English rule in commit messages.** A check beside `check-dco.sh` would catch the cases that reach git history, with the limit that it cannot reach pull requests, issues or comments.
6. **Module boundaries, and test scope for `nkap-conformance` and `nkap-test-support`.** They match today. A boundary nothing checks drifts without anyone choosing it, and the table already understates `server`.
7. **Branch name, `Closes #N`, `@DisplayName`.** Each is mechanical and unchecked, and each is cheap on its own.
8. **The by-hand release steps with a mechanical half:** the version a reader copies, the two independent versions, the API-compatibility rule, and reopening `-SNAPSHOT`. The procedure already gives the commands, and a release is rare, so these cost least when they are missed once.
9. **A new provider module with no conformance subclass or provider page.** Two adapters exist and both comply, so this waits for a third.
10. **ADR amendments.** The shape is mechanical and the content is judgment; the first half is worth checking only if amendments become frequent.
