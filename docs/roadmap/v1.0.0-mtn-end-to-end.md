# v1.0.0 — MTN, end to end

This is the definition of done for the first release, written down so that it stops being
an intuition. Nothing on this list is optional; nothing off it belongs in 1.0.0 however
tempting. When every box is ticked, the release is cut and the project is announced.

The bet behind this scope: a gateway that genuinely works with one operator is a far
stronger invitation to contributors than a mechanism with eight easy issues. Adding Orange
Money, Wave or M-Pesa is the contribution this architecture was built to accept, and it is
worth more to whoever makes it than writing a simulator scenario.

**Announcement happens at 1.0.0, not before.** There is one first impression.

---

## 1. Simulator — the ground truth for every test

- [ ] Configurable latency (#4)
- [ ] Timeout, then late success (#3)
- [ ] Duplicate callback (#5)
- [ ] Callback before the submit response (#6)
- [ ] Callback for an unknown reference (#7)
- [ ] Flapping status (#8)
- [ ] Token expiry mid-flight (#9)
- [ ] Scenarios loaded from YAML files (#10)
- [ ] Callback delivery implemented, not merely modelled
- [ ] Published as a Docker image, usable standalone by developers who will never run the
      gateway

## 2. MTN adapter — complete, not partial

- [ ] Collections: request to pay, status, callback
- [ ] Disbursements: transfer, status, callback
- [ ] Account balance
- [ ] Account holder validation (`isaccountholderactive`)
- [ ] Token lifecycle: cached, renewed ahead of expiry, never on the first 401
- [ ] **Multi-country.** MTN operates across roughly twenty countries with distinct
      subscription keys and target environments. One deployment must serve several without
      a second adapter.
- [ ] The complete status and error mapping, documented in
      `docs/providers/mtn.md` — including every code that maps to `UNKNOWN` rather than to
      a failure
- [ ] The operator's quirks written down: undocumented codes, fields that are sometimes
      absent, sandbox behaviour that differs from production

## 3. The core, persisted

- [ ] Ledger in PostgreSQL, with the invariants as **database constraints**: an entry
      whose postings do not sum to zero cannot be inserted, and entries cannot be updated
      or deleted. A rule that lives only in Java is one a migration script walks through.
- [ ] Idempotency store persisted, with the same four outcomes as the in-memory reference
- [ ] Payment state and its history persisted; every transition attributable
- [ ] Transactional outbox in the same database (ADR 0003)
- [ ] Schema migrations, versioned and reversible

## 4. Operations — what makes it a system rather than a library

- [ ] Reconciler for `UNKNOWN` payments: exponential backoff, a configurable window,
      escalation to a human rather than an automatic verdict
- [ ] Statement reconciliation: import an operator statement, compare it to the ledger,
      produce a discrepancy report
- [ ] Refunds as reversing entries — never as an edit
- [ ] Outgoing webhooks: HMAC-SHA256 signature with a timestamp, at-least-once delivery,
      exponential backoff, dead-letter queue, replay from the console or the API
- [ ] Prometheus metrics, including **the suspense account balance** — the single most
      useful alert in the system
- [ ] Structured logs correlated by reference across every component

## 5. Conformance kit — the door held open for the second operator

- [ ] The same reference submitted twice produces one payment
- [ ] A duplicate callback produces one state transition
- [ ] A callback arriving before the submit response is not lost
- [ ] A callback for an unknown reference is rejected without writing anything
- [ ] A timeout followed by a successful query resolves to `SUCCEEDED`, never `FAILED`
- [ ] A flapping status never reopens a terminal payment
- [ ] An expired token mid-flight is renewed and the call retried with the same reference
- [ ] Runnable against any adapter by a maintainer who has no account with that operator

## 6. Adoption — the first thirty minutes of a stranger

- [ ] `docker compose up` starts the gateway, PostgreSQL and the simulator, and a
      documented command puts one payment through end to end
- [ ] OpenAPI specification, published
- [ ] Integration guide with runnable `curl` examples
- [ ] Configuration reference: every setting, its default, and what happens when it is wrong
- [ ] Kubernetes deployment (Helm chart or Kustomize base)
- [ ] Security notes: credential handling, webhook verification, what Nkap does and does
      not protect

---

## Explicitly out of scope for 1.0.0

Listed so the scope cannot grow quietly. Each of these is a good idea for later.

- **Any operator other than MTN.** Orange Money, Wave, M-Pesa and Airtel come after 1.0.0,
  and they are what contributors are invited to.
- Multi-currency with foreign exchange. One currency per entry, no conversion.
- A merchant dashboard or any user interface.
- KYC, AML, sanctions screening.
- Generated client SDKs.
- Holding funds. Money stays at the operator; Nkap records, it does not custody.
- Becoming a licensed payment institution.

## Definition of done for the release itself

- [ ] Conformance kit green for MTN
- [ ] CI green on `main`
- [ ] `CHANGELOG.md` written
- [ ] Version in the POMs without `-SNAPSHOT`, annotated tag `v1.0.0`, GitHub release
- [ ] Orange Money's API documentation **read** — not implemented — and `provider-api`
      reviewed against it. An adapter contract validated against a single operator is
      probably wrong in a way only the second one reveals, and the first outside
      contributor should not have to discover it in their first pull request.
